# Research: sql-generated-and-identity-columns

Research backing the skill `sql-generated-and-identity-columns`. Each entry: source URL, section,
verbatim quote, and why it matters for the skill. Accessed 2026-06-26.

Two distinct features share the `GENERATED` keyword and are easy to conflate:
1. **Identity columns** — `GENERATED { ALWAYS | BY DEFAULT } AS IDENTITY` — standard surrogate keys.
2. **Generated (computed) columns** — `GENERATED ALWAYS AS (expr) [STORED|VIRTUAL]` — derived values.

---

## A. Identity columns — standard surrogate keys

### A1. PostgreSQL — 5.3. Identity Columns
URL: https://www.postgresql.org/docs/current/ddl-identity-columns.html

**Quote (syntax):**
> "To create an identity column, use the `GENERATED ... AS IDENTITY` clause in `CREATE TABLE`, for example:
> ```
> CREATE TABLE people (
>     id bigint GENERATED ALWAYS AS IDENTITY,
>     ...,
> );
> ```
> or alternatively
> ```
> CREATE TABLE people (
>     id bigint GENERATED BY DEFAULT AS IDENTITY,
>     ...,
> );
> ```"

**Quote (ALWAYS vs BY DEFAULT — the centerpiece):**
> "The clauses `ALWAYS` and `BY DEFAULT` in the column definition determine how explicitly
> user-specified values are handled in `INSERT` and `UPDATE` commands. In an `INSERT` command, if
> `ALWAYS` is selected, a user-specified value is only accepted if the `INSERT` statement specifies
> `OVERRIDING SYSTEM VALUE`. If `BY DEFAULT` is selected, then the user-specified value takes
> precedence."

**Why it matters:** This is the single most load-bearing distinction in the identity half of the
skill. `ALWAYS` protects the surrogate key from accidental app-supplied values (insert fails unless
the writer explicitly opts in with `OVERRIDING SYSTEM VALUE`); `BY DEFAULT` is serial-like and lets a
supplied value win (which is why data loads / replication tools prefer it but it can desync the
sequence). The "broken insert" Who-suffers scenario comes straight from this rule.

### A2. PostgreSQL — 8.1.4. Serial Types
URL: https://www.postgresql.org/docs/current/datatype-numeric.html

**Quote (serial is not a real type):**
> "The data types `smallserial`, `serial` and `bigserial` are not true types, but merely a notational
> convenience for creating unique identifier columns (similar to the `AUTO_INCREMENT` property
> supported by some other databases)."

**Quote (the recommendation — use the standard instead):**
> "This section describes a PostgreSQL-specific way to create an autoincrementing column. Another way
> is to use the SQL-standard identity column feature, described at Section 5.3."

**Why it matters:** Grounds the WRONG=serial / RIGHT=identity framing with a primary-source admission
that `SERIAL` is PostgreSQL-specific syntactic sugar (a hidden `CREATE SEQUENCE` + `DEFAULT
nextval(...)`) and that the SQL-standard identity feature is the documented alternative. This is the
core "prefer the standard" claim.

### A3. modern-sql.com — caniuse generated-always-as-identity / feature list
URL: https://modern-sql.com/caniuse/generated-always-as (related-features list)

**Quote:**
> "`generated [always|by default] as identity` (identity column)"

**Why it matters:** Confirms identity columns are a distinct standard feature (separate from computed
generated columns), vendor-neutrally named. Supports keeping the two halves of the skill cleanly
separated while sharing the `GENERATED` keyword.

## B. Generated (computed) columns — derived values in the schema

### B1. PostgreSQL — 5.4. Generated Columns
URL: https://www.postgresql.org/docs/current/ddl-generated-columns.html

**Quote (syntax):**
> "To create a generated column, use the `GENERATED ALWAYS AS` clause in `CREATE TABLE`, for example:
> ```
> CREATE TABLE people (
>     ...,
>     height_cm numeric,
>     height_in numeric GENERATED ALWAYS AS (height_cm / 2.54)
> );
> ```"

**Quote (STORED vs VIRTUAL, and the view analogy):**
> "A generated column is a special column that is always computed from other columns. Thus, it is for
> columns what a view is for tables. There are two kinds of generated columns: stored and virtual. A
> stored generated column is computed when it is written (inserted or updated) and occupies storage as
> if it were a normal column. A virtual generated column occupies no storage and is computed when it is
> read. Thus, a virtual generated column is similar to a view and a stored generated column is similar
> to a materialized view (except that it is always updated automatically)."

**Quote (cannot reference another generated column):**
> "A generation expression cannot reference another generated column."

**Quote (cannot be written directly):**
> "A generated column cannot be written to directly. In `INSERT` or `UPDATE` commands, a value cannot
> be specified for a generated column, but the keyword `DEFAULT` may be specified."

**Why it matters:** The STORED-vs-VIRTUAL tradeoff (disk vs compute-on-read), the can't-reference-
another-generated-column restriction, and the can't-write-it-directly rule are three of the skill's
numbered points. The "view / materialized view" analogy is a great mental model to teach. NOTE on
engine support: PostgreSQL historically supported only STORED; modern-sql's compatibility chart (B4)
still shows PostgreSQL 18 with no storage-option syntax beyond STORED, so the skill states PG = STORED
only as the portability-relevant fact.

### B2. SQLite — Generated Columns
URL: https://www.sqlite.org/gencol.html

**Quote (VIRTUAL is the default; syntax):**
> "If the trailing "VIRTUAL" or "STORED" keyword is omitted, then VIRTUAL is the default."

> "The "GENERATED ALWAYS" keywords at the beginning of the constraint and the "VIRTUAL" or "STORED"
> keyword at the end are all optional. Only the "AS" keyword and the parenthesized expression are
> required."

**Quote (VIRTUAL vs STORED tradeoff — section 2.1):**
> "Generated columns can be either VIRTUAL or STORED. The value of a VIRTUAL column is computed when
> read, whereas the value of a STORED column is computed when the row is written. STORED columns take
> up space in the database file, whereas VIRTUAL columns use more CPU cycles when being read."

**Quote (read-only nature — section 1):**
> "Generated columns can be read, but their values can not be directly written. The only way to change
> the value of a generated column is to modify the values of the other columns used to calculate the
> generated column."

**Quote (restrictions — section 2.3):**
> "The expression of a generated column may only reference constant literals and columns within the
> same row, and may only use scalar deterministic functions. The expression may not use subqueries,
> aggregate functions, window functions, or table-valued functions."

> "Every table must have at least one non-generated column."

> "Generated columns may not have a default value (they may not use the "DEFAULT" clause)."

**Why it matters:** SQLite is the engine where VIRTUAL is the *default*, the opposite of intuition for
people coming from "computed = stored." The CPU-vs-disk tradeoff is stated crisply. The determinism /
same-row restriction explains why you can't push arbitrary app logic into a generated column.

### B3. MySQL — Generated columns (CREATE TABLE)
URL: https://dev.mysql.com/doc/refman/8.0/en/create-table-generated-columns.html

**Quote (both kinds; VIRTUAL default):**
> "VIRTUAL: Column values are not stored, but are evaluated when rows are read ... A virtual column
> takes no storage. STORED: Column values are evaluated and stored when rows are inserted or updated. A
> stored column does require storage space and can be indexed. The default is VIRTUAL if neither
> keyword is specified."

**Quote (GENERATED ALWAYS optional keyword):**
> "`AS` may be preceded by `GENERATED ALWAYS` to make the generated nature of the column more explicit."

**Why it matters:** Grounds the portability row: MySQL supports both STORED and VIRTUAL with VIRTUAL as
default (like SQLite), and uses `AUTO_INCREMENT` rather than identity columns for surrogate keys.

### B4. modern-sql.com — caniuse / generated columns
URL: https://modern-sql.com/caniuse/generated-always-as

**Quote (SQL standard feature id):**
> "ISO/IEC 9075-2:2023 as optional feature T175."

**Quote (the deterministic-so-timing-is-an-implementation-choice point):**
> "The DBMS could also spare that space and just calculate the value when it is queried. As a
> generation expression has to be deterministic, in principle, it doesn't matter when it is evaluated."

**Engine support (from the compatibility chart):** PostgreSQL 18 shows no STORED/VIRTUAL storage-option
syntax beyond STORED; MySQL 9.x, Oracle 23c, SQL Server 2025, DuckDB, SQLite 3.53 accept the syntax;
DB2 accepts all spellings (persisted/persistent/materialized/stored/virtual).

**Why it matters:** Vendor-neutral confirmation that generated columns are a standardized optional
feature (T175, SQL:2023 codification), that the STORED/VIRTUAL choice is "just" a when-to-evaluate
decision because the expression must be deterministic, and the cross-engine support matrix backing the
portability block.

## C. Synthesis — the skill's load-bearing claims and where each is grounded

1. **Prefer standard `GENERATED ... AS IDENTITY` over `SERIAL`/`AUTO_INCREMENT`/`IDENTITY(1,1)`.**
   Grounded: A2 (PG calls serial "not a true type" and points to the SQL-standard feature), A1, A3.

2. **`ALWAYS` rejects explicit inserts (needs `OVERRIDING SYSTEM VALUE`); `BY DEFAULT` accepts them.**
   Grounded: A1 (verbatim).

3. **Computed columns: `GENERATED ALWAYS AS (expr) STORED|VIRTUAL`; STORED = disk/compute-on-write,
   VIRTUAL = compute-on-read.** Grounded: B1, B2 (2.1), B3.

4. **Engine support differs:** PG = STORED only; SQLite = both, VIRTUAL default; MySQL = both, VIRTUAL
   default + AUTO_INCREMENT for keys. Grounded: B1, B2, B3, B4.

5. **A generated column cannot be written directly** (INSERT/UPDATE may only supply `DEFAULT`).
   Grounded: B1, B2 (1).

6. **A generated column cannot reference another generated column; expression must be deterministic
   and same-row.** Grounded: B1, B2 (2.3).

7. **Push derivation into the schema, not into every query / every app write path** — the engine keeps
   it consistent automatically (B1 "always computed", "always updated automatically"); modern-sql notes
   determinism makes the storage timing a pure implementation choice (B4). This anchors the
   "derivation in schema, not app" section and the drift-bug Who-suffers scenario.
