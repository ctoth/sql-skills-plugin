Anti-patterns in LLM-generated SQL around identity columns and computed (generated) columns, each with
wrong/right code and a primary-source citation. The skill (`sql-generated-and-identity-columns`) states
the rules; this file holds the high-frequency failure modes. All RIGHT examples are standard/portable
SQL; non-standard spellings are flagged and routed to `sql-standard-vs-dialect-map`.

## 1. Reaching for `SERIAL`/`AUTO_INCREMENT` instead of a standard identity column

**The problem:** The model writes `id SERIAL` (PostgreSQL) or `id INT AUTO_INCREMENT` (MySQL) or `id INT IDENTITY(1,1)` (SQL Server) out of habit. These are vendor-specific and don't port. PostgreSQL itself says `serial` and friends "are not true types, but merely a notational convenience ... Another way is to use the SQL-standard identity column feature" ([PostgreSQL — Serial Types](https://www.postgresql.org/docs/current/datatype-numeric.html)).

```sql
-- WRONG — non-standard sugar; a hidden sequence + DEFAULT nextval() under the hood
CREATE TABLE people (id SERIAL PRIMARY KEY, name text NOT NULL);

-- RIGHT — the SQL-standard identity column
CREATE TABLE people (
    id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text   NOT NULL
);
```

*Source: [PostgreSQL — Serial Types](https://www.postgresql.org/docs/current/datatype-numeric.html); [PostgreSQL — Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html). Depth: this skill, §1; dialect mapping owned by `sql-standard-vs-dialect-map`.*

## 2. Supplying an explicit `id` into a `GENERATED ALWAYS AS IDENTITY` column

**The problem:** The ORM or generated SQL sends a value for the identity column. With `ALWAYS`, "a user-specified value is only accepted if the `INSERT` statement specifies `OVERRIDING SYSTEM VALUE`" — otherwise the insert errors ([PostgreSQL — Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html)). The model often "fixes" the error by switching the column to `BY DEFAULT`, which silently invites key collisions later (a supplied value doesn't advance the sequence).

```sql
-- WRONG — fails against GENERATED ALWAYS: the value is not accepted
INSERT INTO people (id, name) VALUES (42, 'Ada');

-- RIGHT — let the engine assign the key (omit the column, or pass DEFAULT)
INSERT INTO people (name) VALUES ('Ada');
INSERT INTO people (id, name) VALUES (DEFAULT, 'Ada');

-- RIGHT — only when you truly must force a value (bulk load / migration): opt in
INSERT INTO people (id, name) OVERRIDING SYSTEM VALUE VALUES (42, 'Ada');
```

*Source: [PostgreSQL — Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html). Depth: this skill, §2.*

## 3. Choosing `BY DEFAULT` when `ALWAYS` was wanted (unprotected key)

**The problem:** The model defaults to `GENERATED BY DEFAULT AS IDENTITY` everywhere. `BY DEFAULT` lets a user-specified value take precedence ([PostgreSQL — Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html)), so app code can set keys and a later auto-generated value can collide with one that was supplied. Use `ALWAYS` to protect the surrogate key; reserve `BY DEFAULT` for tools that must insert explicit keys (e.g. restoring a dump).

```sql
-- WRONG (as a blanket default) — app code can set the key; collisions await
id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY

-- RIGHT — the engine owns the key; explicit values are rejected unless overridden
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

*Source: [PostgreSQL — Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html). Depth: this skill, §2.*

## 4. Storing a derived value in a plain column the app maintains by hand

**The problem:** The model adds a normal column (`total`, `full_name`, `age`) and computes it in application code on insert/update. Any missed write path — a bulk update, a second service, a manual SQL fix — leaves it stale and out of sync with its inputs. A generated column is "always computed from other columns" and a stored one is "always updated automatically" ([PostgreSQL — Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html)).

```sql
-- WRONG — plain column; correctness depends on every writer remembering to recompute
ALTER TABLE orders ADD COLUMN total numeric;   -- set in app code ... usually

-- RIGHT — the engine maintains it on every write; cannot drift
ALTER TABLE orders ADD COLUMN total numeric GENERATED ALWAYS AS (price * qty) STORED;
```

*Source: [PostgreSQL — Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html). Depth: this skill, §6.*

## 5. Trying to INSERT/UPDATE a value into a generated column

**The problem:** The model includes the generated column in the column list and supplies a value. "A generated column cannot be written to directly. In `INSERT` or `UPDATE` commands, a value cannot be specified for a generated column, but the keyword `DEFAULT` may be specified" ([PostgreSQL — Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html)).

```sql
-- WRONG — total is derived; supplying it is an error
INSERT INTO line_items (price, qty, total) VALUES (10, 3, 30);
UPDATE line_items SET total = 99 WHERE id = 1;

-- RIGHT — write only the inputs; the engine computes the generated column
INSERT INTO line_items (price, qty) VALUES (10, 3);
UPDATE line_items SET qty = 5 WHERE id = 1;   -- total recomputes automatically
```

*Source: [PostgreSQL — Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html); [SQLite — Generated Columns](https://www.sqlite.org/gencol.html). Depth: this skill, §5.*

## 6. Omitting `STORED`/`VIRTUAL` and assuming the result is portable

**The problem:** The model writes `GENERATED ALWAYS AS (expr)` with no storage keyword and assumes one behavior. The default differs by engine: SQLite and MySQL default to **VIRTUAL** ("If the trailing `VIRTUAL` or `STORED` keyword is omitted, then `VIRTUAL` is the default" — [SQLite](https://www.sqlite.org/gencol.html); "The default is `VIRTUAL` if neither keyword is specified" — [MySQL](https://dev.mysql.com/doc/refman/8.0/en/create-table-generated-columns.html)), while PostgreSQL supports only STORED and requires it. Same DDL, different storage and indexability.

```sql
-- WRONG — implicit storage; means VIRTUAL on SQLite/MySQL, won't run as-is on PostgreSQL
height_in numeric GENERATED ALWAYS AS (height_cm / 2.54)

-- RIGHT — say which, every time
height_in numeric GENERATED ALWAYS AS (height_cm / 2.54) STORED    -- on disk, indexable
full_name text    GENERATED ALWAYS AS (first || ' ' || last) VIRTUAL  -- compute on read
```

*Source: [SQLite — Generated Columns](https://www.sqlite.org/gencol.html); [MySQL — Generated Columns](https://dev.mysql.com/doc/refman/8.0/en/create-table-generated-columns.html); [PostgreSQL — Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html). Depth: this skill, §4, §7; defaults table routed to `sql-standard-vs-dialect-map`.*

## 7. A generation expression that references another generated column

**The problem:** The model chains computed columns: a generated `b` that references generated `a`. "A generation expression cannot reference another generated column" ([PostgreSQL — Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html)). Reference the base columns instead.

```sql
-- WRONG — net references the generated column subtotal
subtotal numeric GENERATED ALWAYS AS (price * qty) STORED,
net      numeric GENERATED ALWAYS AS (subtotal * 0.9) STORED   -- references a generated col

-- RIGHT — both derive from the base columns
subtotal numeric GENERATED ALWAYS AS (price * qty) STORED,
net      numeric GENERATED ALWAYS AS (price * qty * 0.9) STORED
```

*Source: [PostgreSQL — Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html). Depth: this skill, §3, §5.*

## 8. Putting non-deterministic or cross-row logic in a generated column

**The problem:** The model writes a generated column whose expression calls `now()`, a subquery, or an aggregate ("sum of this customer's orders"). The expression "may only reference constant literals and columns within the same row, and may only use scalar deterministic functions ... may not use subqueries, aggregate functions, window functions, or table-valued functions" ([SQLite — Generated Columns](https://www.sqlite.org/gencol.html)). Cross-row or time-varying derivations belong in a view or query.

```sql
-- WRONG — non-deterministic and cross-row; not allowed in a generation expression
age          int     GENERATED ALWAYS AS (date_part('year', age(now(), birth_date))) STORED,
order_total  numeric GENERATED ALWAYS AS ((SELECT sum(amount) FROM orders o WHERE o.cust = id)) STORED

-- RIGHT — same-row, deterministic derivations only
full_name    text    GENERATED ALWAYS AS (first_name || ' ' || last_name) STORED,
line_total   numeric GENERATED ALWAYS AS (price * qty) STORED
-- compute age / per-customer totals in a query or view instead
```

*Source: [SQLite — Generated Columns](https://www.sqlite.org/gencol.html). Depth: this skill, §3.*
