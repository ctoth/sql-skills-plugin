# Common SQL Portability Mistakes

High-frequency portability failures in LLM-generated SQL — the model writes a spelling
that parses on *one* engine and fails (or silently misbehaves) on the target. Each has
wrong/right code and a primary-source citation. The parent skill
(`sql-standard-vs-dialect-map`) holds the full matrix; this file holds the recurring
"shipped to the wrong engine" failure modes. Where a portable standard spelling exists,
the RIGHT example uses it.

---

## 1. Shipping `LIMIT` to Oracle (pre-12c) or SQL Server

**The problem:** `LIMIT` is ubiquitous but **non-standard** and absent on Oracle before 12c and on SQL Server. The model ports a PostgreSQL/MySQL query unchanged and it fails to parse.

```sql
-- WRONG — ORA-00933 on Oracle 11g; syntax error on SQL Server
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;

-- RIGHT — the SQL standard pagination clause (PG, Oracle 12c+, SQL Server 2012+, DuckDB)
SELECT * FROM orders ORDER BY created_at DESC
OFFSET 0 ROWS FETCH FIRST 10 ROWS ONLY;
```

*Source: [PostgreSQL — LIMIT/FETCH](https://www.postgresql.org/docs/current/sql-select.html#SQL-LIMIT); [antonz.org — SQL FETCH](https://antonz.org/sql-fetch/). Depth: `sql-pagination-and-keyset`.*

## 2. Double-quoted strings (the SQLite/MySQL → PostgreSQL break)

**The problem:** `"abc"` is a *string literal* in MySQL's default mode and tolerated in SQLite, but a *quoted identifier* (column/table name) in the standard and PostgreSQL. The query passes review and CI on MySQL, then errors as "column does not exist" on PostgreSQL.

```sql
-- WRONG — "active" is read as a COLUMN NAME on PostgreSQL
SELECT * FROM tasks WHERE status = "active";

-- RIGHT — single quotes are a string literal on every engine
SELECT * FROM tasks WHERE status = 'active';
```

*Source: [PostgreSQL — Lexical Structure](https://www.postgresql.org/docs/current/sql-syntax-lexical.html); [MySQL — String Literals / ANSI_QUOTES](https://dev.mysql.com/doc/refman/8.0/en/string-literals.html). Depth: `sql-style-and-naming`.*

## 3. Reusing one engine's upsert syntax on another

**The problem:** `ON DUPLICATE KEY UPDATE` is MySQL-only; `ON CONFLICT` is PG/SQLite-only; `MERGE` reached PostgreSQL only in 15. The model rewrites a warehouse and the upsert throws a syntax error.

```sql
-- WRONG on PostgreSQL — ON DUPLICATE KEY UPDATE is MySQL-only
INSERT INTO counters (id, n) VALUES (1, 1)
ON DUPLICATE KEY UPDATE n = n + 1;

-- RIGHT on PostgreSQL / SQLite
INSERT INTO counters (id, n) VALUES (1, 1)
ON CONFLICT (id) DO UPDATE SET n = counters.n + 1;

-- RIGHT on MySQL (note the different new-value alias)
INSERT INTO counters (id, n) VALUES (1, 1) AS new
ON DUPLICATE KEY UPDATE n = counters.n + 1;
```

*Source: [PostgreSQL — INSERT ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html); [MySQL — INSERT ON DUPLICATE KEY UPDATE](https://dev.mysql.com/doc/refman/8.0/en/insert-on-duplicate.html). Depth: `sql-merge-and-upsert`.*

## 4. `EXCEPT` on Oracle (it is spelled `MINUS`)

**The problem:** Oracle spells set difference `MINUS`, not `EXCEPT`. The model emits the standard keyword and Oracle rejects it.

```sql
-- WRONG on Oracle — EXCEPT is not a keyword there
SELECT id FROM a EXCEPT SELECT id FROM b;

-- RIGHT on Oracle
SELECT id FROM a MINUS SELECT id FROM b;
-- (EXCEPT is correct on PostgreSQL/SQLite; MySQL only 8.0.31+)
```

*Source: [Oracle — Set Operators (MINUS)](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/The-UNION-ALL-INTERSECT-MINUS-Operators.html); [SQLite — compound select](https://www.sqlite.org/lang_select.html#compound_select_statements). Depth: `sql-set-operations`.*

## 5. `SERIAL` is not portable — and is legacy even on PostgreSQL

**The problem:** The model writes `SERIAL` everywhere. SQLite and MySQL do not have it, and PostgreSQL itself now recommends the standard `GENERATED AS IDENTITY`.

```sql
-- WRONG cross-engine — SERIAL is PostgreSQL-specific
CREATE TABLE t (id SERIAL PRIMARY KEY);

-- RIGHT on PostgreSQL (10+) — the SQL standard spelling
CREATE TABLE t (id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY);
-- SQLite:  id INTEGER PRIMARY KEY            (rowid alias)
-- MySQL:   id INT AUTO_INCREMENT PRIMARY KEY
```

*Source: [PostgreSQL — Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html); [SQLite — rowid](https://www.sqlite.org/lang_createtable.html#rowid). Depth: `sql-generated-and-identity-columns`.*

## 6. `NOW()` instead of `CURRENT_TIMESTAMP`

**The problem:** `NOW()` is PG/MySQL; SQL Server uses `GETDATE()`, Oracle `SYSDATE`, SQLite `datetime('now')`. The standard `CURRENT_TIMESTAMP` works on all of them.

```sql
-- WRONG cross-engine — NOW() is not universal
INSERT INTO log (at) VALUES (NOW());

-- RIGHT — the standard special register, portable everywhere
INSERT INTO log (at) VALUES (CURRENT_TIMESTAMP);
```

*Source: [PostgreSQL — Current Date/Time](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT). Depth: `sql-datetime-and-intervals`.*

## 7. Assuming `BOOLEAN` exists everywhere / bare-boolean `WHERE`

**The problem:** Only PostgreSQL (and DuckDB) have a true `BOOLEAN`. MySQL maps it to `TINYINT(1)`, SQL Server uses `BIT`, SQLite stores integer 0/1 — and none of those accept a bare `WHERE active`.

```sql
-- WRONG on SQL Server / MySQL — bare boolean column is not a predicate
SELECT * FROM users WHERE active;

-- RIGHT — compare explicitly; portable across the 0/1 engines
SELECT * FROM users WHERE active = 1;   -- or = TRUE only where BOOLEAN is real
```

*Source: [PostgreSQL — Boolean Type](https://www.postgresql.org/docs/current/datatype-boolean.html); [MySQL — Boolean = TINYINT(1)](https://dev.mysql.com/doc/refman/8.0/en/numeric-type-syntax.html). Depth: `sql-data-types-and-numerics`.*

## 8. `IS DISTINCT FROM` on MySQL (use `<=>`)

**The problem:** The standard null-safe equality `IS NOT DISTINCT FROM` does not exist on MySQL, which spells it `<=>`. SQLite's bare `IS` already compares NULLs as equal.

```sql
-- WRONG on MySQL — IS NOT DISTINCT FROM is not recognized
SELECT * FROM a JOIN b ON a.k IS NOT DISTINCT FROM b.k;

-- RIGHT on MySQL
SELECT * FROM a JOIN b ON a.k <=> b.k;
-- PostgreSQL/standard: a.k IS NOT DISTINCT FROM b.k ;  SQLite: a.k IS b.k
```

*Source: [MySQL — `<=>`](https://dev.mysql.com/doc/refman/8.0/en/comparison-operators.html). Depth: `sql-relational-and-null-discipline` §8.*

## 9. `INFORMATION_SCHEMA` on SQLite or Oracle

**The problem:** The model introspects with `INFORMATION_SCHEMA`, which SQLite and Oracle do not have. SQLite uses `sqlite_master`/`PRAGMA`; Oracle uses its data dictionary.

```sql
-- WRONG on SQLite — no INFORMATION_SCHEMA
SELECT table_name FROM information_schema.tables;

-- RIGHT on SQLite
SELECT name FROM sqlite_master WHERE type = 'table';
-- columns:  PRAGMA table_info('mytable');
-- Oracle:   SELECT table_name FROM all_tables;
```

*Source: [SQLite — `sqlite_schema`](https://www.sqlite.org/schematab.html); [SQLite — PRAGMA](https://www.sqlite.org/pragma.html#pragma_table_info). Depth: `sql-views-and-introspection`.*

## 10. `->` / `->>` JSON operators on Oracle (and `JSON_VALUE` on old engines)

**The problem:** The `->`/`->>` operators are vendor extensions absent on Oracle, and the standard `JSON_VALUE`/`JSON_TABLE` functions are version-gated (PG only 17+, MySQL `JSON_VALUE` 8.0.21+). The model picks one spelling and it is missing on the target.

```sql
-- WRONG on Oracle / pre-3.38 SQLite — no -> / ->> operator
SELECT data ->> 'email' FROM users;

-- RIGHT on SQLite (all versions) / portable extract
SELECT json_extract(data, '$.email') FROM users;
-- Oracle / standard:  SELECT JSON_VALUE(data, '$.email') FROM users;
```

*Source: [SQLite — JSON functions](https://www.sqlite.org/json1.html); [PostgreSQL — JSON Functions](https://www.postgresql.org/docs/current/functions-json.html). Depth: `sql-json`.*

## 11. Relying on the default isolation level being the same everywhere

**The problem:** The model writes transaction code without setting an isolation level, assuming uniform behavior. PostgreSQL defaults to `READ COMMITTED`, MySQL/InnoDB to `REPEATABLE READ`, SQLite to `SERIALIZABLE` — so a concurrency anomaly reproduces on one engine only.

```sql
-- WRONG (assumption) — same code, different isolation per engine
BEGIN;  -- PG: READ COMMITTED, MySQL: REPEATABLE READ, SQLite: SERIALIZABLE
  SELECT balance FROM accounts WHERE id = 1;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- RIGHT — set the level explicitly so behavior is portable
BEGIN;
  SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  -- ... read-modify-write ...
COMMIT;
```

*Source: [PostgreSQL — Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html); [SQLite — Isolation](https://www.sqlite.org/isolation.html). Depth: `sql-transactions-and-isolation`.*

## 12. `FULL JOIN` on MySQL

**The problem:** MySQL has no `FULL [OUTER] JOIN`. The model writes one and MySQL rejects it; PostgreSQL and SQLite (3.39.0+) accept it.

```sql
-- WRONG on MySQL — FULL JOIN is unsupported
SELECT * FROM a FULL OUTER JOIN b ON a.k = b.k;

-- RIGHT on MySQL — emulate with LEFT + RIGHT union
SELECT * FROM a LEFT JOIN b ON a.k = b.k
UNION
SELECT * FROM a RIGHT JOIN b ON a.k = b.k;
```

*Source: [MySQL — JOIN](https://dev.mysql.com/doc/refman/8.0/en/join.html); [SQLite — RIGHT/FULL JOIN 3.39.0](https://www.sqlite.org/releaselog/3_39_0.html). Depth: `sql-joins`.*
